## Design decisions

- D1 Re-cut instead of base-moved at the start of an invocation. When a journal exists with `merge` null, the engine reads the authoritative remote base once. If it differs from `record.baseHead`, and the bound PR (if any) is OPEN and not in a merge queue, the engine re-cuts under the same version instead of refusing: it re-audits the new base (`audit(rolled.notes,true,newBase)`, refusing `missing-notes` as a fresh cut does), rebuilds the rollup of `newBase:CHANGELOG.md`, commits it on a new release commit whose only parent is `newBase`, runs the preflight (D6), pushes it to the same branch under a lease on the old head, and keeps the same PR. A queued PR stays `PENDING: merge-queue`. A pre-PR journal (stages `initialized` to `pushed`) re-cuts the same way; the lease is on the recorded head when it was pushed, and on an absent branch otherwise.
- D2 Guards, each named by what it compares. Before any write the re-cut compares and refuses:
  - `head-moved`: the remote release-branch head, read with `git ls-remote`, against the journal's head (and, on resume, the pending re-cut's new head). The refusal names both SHAs.
  - `head-moved` (local): the local `refs/heads/chore/release-<v>`, when it exists, against the journal's head; it is moved only with a compare-and-swap `git update-ref` from that head.
  - `identity`: the bound PR's state from `gh pr view` against OPEN. A CLOSED PR refuses; a MERGED PR is never re-cut and continues to publication with its merged content.
  - `tag-exists`: `refs/tags/<v>`, read locally and with `git ls-remote --tags`, against absent. A published version is never re-cut.
  - `base-rewritten`: `git merge-base --is-ancestor <old baseHead> <new base>`. A base that no longer contains the audited base refuses.
  The push itself carries `--force-with-lease=refs/heads/<branch>:<old head>`, so a branch move between the comparison and the push makes git refuse the push. Caveat that applies to every guard here: each compares what it reads at that moment; GitHub can still change between the read and the next call, and the lease is the only atomic comparison.
- D3 Journal schema, additive. New optional keys: `recut` (absent or null, or exactly `{fromBase, fromHead}` with full SHAs; `fromHead` may be null for a never-pushed pre-PR journal) and `recuts` (absent or an array of exactly `{fromBase, toBase, fromHead, toHead, at}`, SHAs full, `at` ISO-8601 UTC). The stage list gains `recut`. A journal without these keys (the live v2026.10.26 journal) loads unchanged. Order of writes: one atomic journal write sets `recut`, the new `baseHead`, `content`, `notes`, `head: null` and stage `recut`; the existing preparation path then commits and journals the new head; after the leased push, one atomic write appends the `recuts` entry and clears `recut`. A run interrupted at any point resumes from the journal: a remote head equal to the new head is adopted, a remote head equal to `recut.fromHead` is pushed again under the same lease, anything else refuses `head-moved`.
- D4 The PR follows the branch. After the push the engine waits, bounded by `AAI_RELEASE_WAIT_SECONDS` and polled every `AAI_RELEASE_POLL_SECONDS`, until `gh pr view` reports `headRefOid` equal to the new head (GitHub updates it asynchronously), then rewrites the PR body with `gh pr edit --body-file`: the existing bound-release text with the new head, its `no-notes:` line, and one line `Re-cut: <fromHead> on <fromBase> -> <toHead> on <toBase>.` per journal `recuts` entry. Required contexts and checks are then read for the new head as today; the merge keeps `--match-head-commit` on the journal head.
- D5 A base move after the CI wait still refuses, with the same-version remedy. The pre-merge comparison (line 528) keeps cause `base-moved` but its detail becomes `Remote release base moved while CI ran; re-run this same --version --confirm to re-cut it on the new base`. The next invocation re-cuts per D1. One re-cut per invocation; no in-run loop. The required-checks refusal on an open release PR gains `; fix the failure on <base> and re-run this same --version`.
- D6 Release preflight on the rolled payload, before every push of a release head. Selection: every path tracked in the release commit that has a `tests` path segment, ends in `.test.mjs`, and whose blob at that commit contains the bytes `CHANGELOG`. For each selected file, in a disposable detached worktree of the release commit, the engine runs `node --test <file>` with a timeout of `AAI_RELEASE_PREFLIGHT_SECONDS` (default 900; unset or blank means the default; a value that is not a plain decimal refuses `arguments`). A file that fails is re-run in a disposable detached worktree of the base commit. Rolled fails and base passes: refuse `release-preflight` naming the file and `fails only on the rolled payload`, with the last 20 output lines; nothing is pushed and the journal keeps the unpushed head, so a resume after the fix lands re-cuts. Rolled fails and base fails too: print `- Release preflight: <file> FAILS ON BASE TOO (not caused by the rollup; CI decides)` and continue. A timeout counts as a failure of that run. No selected file: print `- Release preflight: SKIPPED (no tracked tests/**/*.test.mjs reads CHANGELOG)`. Both worktrees are removed with a targeted `git worktree remove --force <path>`, never `prune`. Shell and PowerShell suites are not run (cost, see Measurements); they remain CI's job, and D1 makes their failure cheap to recover.
- D7 Texts. No refusal, prompt or product text tells the operator to cut a new `--version` while the release can still be finished. The bound closed-PR detail becomes `Bound release PR #<n> is closed without merge; reopen it and re-run this same --version`. The no-journal closed-PR detail keeps the phrase `is closed without a matching journal` (a SPEC-0236 mutation anchor) and becomes `Release PR #<n> on chore/release-<v> is closed without a matching journal; delete branch chore/release-<v> and re-run this same --version`. The line-352 detail `prepare a newly audited release` disappears with D1. SKILL_RELEASE gets no larger than 4921 bytes (its size at 20ee3591), so no prompt-diet ledger entry is owed.
- D8 Frontends. No new flags. `aai-release.sh` and `aai-release.ps1` keep exec-ing the engine; their header comments name the re-cut and the preflight in one line each; exit codes unchanged.
- D9 Never touched: a merged PR (no re-cut), a tag (refused), `main` (only the existing narrow base-sync transaction writes it), any branch other than `chore/release-<v>`.
- D10 Supersession without editing done specs. SPEC-0233 and SPEC-0236 stay frozen as written. Their suite assertions are updated where this scope changes the observed text (SPEC-0236 TEST-083 detail strings); SPEC-0233 TEST-015's product-doc pattern `fresh audited cut|deliberate repair` and `base-moved` stay satisfied because the new product text names the re-cut as the deliberate repair and keeps naming `base-moved`; SPEC-0233 TEST-016's in-run base-move arm still refuses `base-moved` per D5. The orchestrator decides whether to record a contract `spec_amendment` against SPEC-0236; this spec discloses the change here.

## Implementation plan

Components: `.aai/scripts/release-finish.mjs`; `tests/skills/test-aai-release.sh` (stub, fixture modes, new cases); `.aai/SKILL_RELEASE.prompt.md`; `docs/product/release-command-finish.md`; `docs/USER_GUIDE.md` (the release recovery paragraph near line 745); the header comments of `aai-release.sh` and `aai-release.ps1`; one `## [unreleased] — <title>` CHANGELOG entry at ship time.

1. Journal (D3). Extend `journalShape()` with the optional `recut` and `recuts` shapes and the stage literal `'recut',` (exactly once in the file, inside the stage list). Strict: unknown keys inside `recut` or a `recuts` entry make the journal `journal-corrupt`.
2. Re-cut entry (D1, D2). One function `recutIfMoved()` runs after the journal loads and before preparation, for `record.merge===null`. It reads the PR when `record.pr` is set; its first PR test is the literal `if(pr.state==='MERGED')return;`; a CLOSED PR refuses with the D7 text; a queued PR is pending. It reads the moved base into `moved` and calls the literal `if(moved)recutRelease(moved);`. `recutRelease` checks, in order, the literals `if(tagSeen)refuse('tag-exists',`, `if(!descends)refuse('base-rewritten',`, and `if(remote!==record.recut.fromHead&&remote!==record.head)refuse('head-moved',` (on resume the second operand admits the already pushed new head), re-audits, compare-and-swaps the local branch ref, writes the D3 journal state and returns to the existing preparation path (`!record.head`). Replace both `unchangedBase()` call sites at lines 466 and 520 with this entry; keep line 528's check with the D5 text.
3. Push (D2, D6). Both pushes (first cut and re-cut) go through one `pushRelease()` whose first statement is the literal `releasePreflight();`. The re-cut push argv contains the literal `` `--force-with-lease=refs/heads/${branch}:${record.recut.fromHead}` ``. After it, the literal `record.recuts.push({fromBase:` and a single atomic save.
4. PR follow-up (D4). Wait with `boundedPoll(...)` whose ready predicate is the literal `p=>p.headRefOid===record.head`, cause `identity`. Then the literal `gh('pr','edit',String(record.pr),'--repo',repo,'--body-file',` with a body written in the journal directory and unlinked in `finally`, like the create body.
5. Preflight (D6). `releasePreflight()` selects with the literal `p.split('/').includes('tests')&&p.endsWith('.test.mjs')` over `git ls-tree -r --name-only <head>` and the literal `text.includes('CHANGELOG')` over each blob; spawns `node --test <file>` with `cwd` the disposable worktree, `timeout:preflightSeconds*1000`; on a rolled failure re-runs at the base and refuses with the literal `if(!baseFails)refuse('release-preflight',`. The env parse copies the existing `checksGrace` parse.
6. Texts (D5, D7). New literals: `re-run this same --version --confirm to re-cut it on the new base`, `reopen it and re-run this same --version`, `fix the failure on`.
7. Stub and fixtures (tests). Teach the gh stub `pr edit 1 --repo test/release --body-file <journal-dir body>` (records the body); make `pr view`/`pr list` report an OPEN PR's `headRefOid` from the bare origin's branch ref (as GitHub does), with a `head-lag` mode that reports the old head on the first read after a push; add modes `ci-first-head` (checks fail while the PR head is the first head, pass afterwards), `closed` (PR #1 CLOSED after creation) and `recut-lease-race` (the git wrapper moves the origin branch when it sees the re-cut push). Base moves use the existing `remoteCommit()`; the rewrite arm uses `git push --force` from a writer clone.
8. Case wiring. The new node cases are selected by a new env `RELEASE_RECUT_CASE=<id>` and run only then (never in the `all` pass), each through a bash wrapper `test_731_…` onward called from `main`, invoked as `RELEASE_FINISH_CASE=none RELEASE_RECUT_CASE=TEST-1xx test_700_one_command_finish`. This keeps SPEC-0236's `ownSelector` literal and TEST-085 untouched. TEST-109 and TEST-110 are plain bash functions. TEST-115 is a plain bash function with an embedded node check that tests the journal entry with the literal `fromHead.startsWith('00c06fcf')`; without `AAI_RELEASE_LIVE_ACCEPTANCE` it prints `SKIP: TEST-115 …` and returns 0.
9. Existing assertions to update, nothing else: TEST-083's expected detail strings (D7). TEST-016, TEST-010, TEST-011, TEST-015, TEST-033 and TEST-060 to TEST-086 must stay green unchanged.

Edge cases decided here: a journal whose `recut` is pending and whose base moved again re-audits the newest base and keeps the original `fromHead` lease; a re-cut never runs while `record.merge` is set; `--dry-run` and bare previews never re-cut or run the preflight; a base equal to `record.baseHead` never re-cuts.

## Seams

- Engine to the fixture origin and GitHub stub: TEST-101 produces the #504 shape end to end (red CI, fix on base, same command) and asserts the real outcome on the other side: the origin's branch, tag and merge commit, and the stub's PR count, edit body and merge argv.
- Engine to GitHub's asynchronous PR head: the `head-lag` mode in TEST-101 makes the stub report the old head once after the push.
- Re-cut to preflight: TEST-106's last arm runs the preflight on a re-cut, not only on a first cut.
- Engine to its own journal across processes: TEST-104 interrupts at each stage with the real engine and resumes with a new process.
- Journal compatibility: TEST-102 starts from a journal written by the pre-change code path shape (no `recut`/`recuts` keys), as the live journal is.
- Frontends: TEST-101 re-runs its arm through `aai-release.ps1` when pwsh is present.
- Rolled payload to the repository's own node tests: TEST-106 runs a real `node --test` file against a rolled fixture tree; V1 replays the live #504 pair.
- Residual risks no automated test crosses: GitHub's real PR-head update latency and `gh pr edit` behavior on a force-pushed head (the live run in Spec-AC-09 is the proof); shell and PowerShell suites that pin `[unreleased]` (not run by the preflight; CI catches them and D1 makes the recovery one command); a base push between the last observation and GitHub's merge (unchanged known external limit, SPEC-0233 TEST-017); a recheck-style test that needs untracked local state passes or fails identically in both worktrees and is then reported as `FAILS ON BASE TOO` rather than blocking.

## Constitution deviations

None.

Article 5: the journal change is additive (absent keys mean no re-cut) and the changed refusal texts are documented in the product doc. Article 7: the engine still merges only the operator-confirmed bound release PR; the new write is a leased update of that PR's own release branch. Article 4: the preflight names a skip and a base-also-failing file on stdout instead of silently passing.
