## Summary

Twice on 2026-08-13 the ride shipped a link to a file that no longer existed.

Measured on the real trees, not inferred:

- At `00bdd03` ("docs(spec): allocate SPEC-0127") — the commit produced BY the
  allocator — `docs/USER_GUIDE.md`, `docs/ai/overview.html` and
  `docs/ai/overview-data.json` each still carried exactly one
  `SPEC-DRAFT-spec-reporting-docs-true-up` reference while
  `docs/specs/SPEC-0127-spec-reporting-docs-true-up.md` existed on disk.
  `docs/INDEX.md` was clean, because the allocator regenerates that one.
- At `ff8208e` ("docs(spec): allocate SPEC-0128") — same shape,
  `docs/ai/overview.html` and `docs/ai/overview-data.json`, one hit each.

The mechanism is a projection seam, not forgetfulness. The allocator renames
`SPEC-DRAFT-<slug>.md` to `SPEC-<NNNN>-<slug>.md` and rewrites every reference
inside its `REWRITE_TREES` — which include the SOURCES (`docs/specs`,
`docs/issues`, `docs/product`, `README.md`, ...). It then regenerates exactly
one PROJECTION of those sources: `docs/INDEX.md`. The other projections —
`docs/USER_GUIDE.md`'s rollup block (generated FROM `docs/product/*.md`, whose
`spec:` frontmatter the allocator just rewrote) and `docs/ai/overview.*`
(generated FROM `docs/specs/*.md`, which the allocator just renamed) — are left
holding the pre-rename path. They are not markdown in a rewrite tree, and they
must not be hand-patched: they are generated.

`close-work-item.mjs` already regenerates overview, the USER_GUIDE rollup,
docs-hub and the factory report (lines 1200-1203), and that did NOT prevent
either incident, because of WHERE it sits in the ride. `.aai/SKILL_PR.prompt.md`
runs the allocator at step 1b, BEFORE staging; the close ceremony runs at step
5c, AFTER `gh pr create`. The stale bytes are committed, pushed and read by the
review bots before the close regen ever fires. Adding more generators to the
close tail would be motion, not a fix.

So the fix goes where the invalidation happens: the rename and the regeneration
become one operation. Detection is added on top, because prevention at one call
site cannot prove the invariant for pages regenerated by any other path.

## Design decisions recorded at planning time (do not re-derive)

### D1 — BOTH prevention and detection; prevention lands in the allocator, and that costs level 3

Three candidates were weighed against the two measured incidents.

Prevention in `close-work-item.mjs` — REJECTED as already-tried. It is the
literal status quo (lines 1200-1203 regenerate overview and the USER_GUIDE
rollup today) and both incidents happened anyway, because close runs after PR
open. Cost of doing it again: zero defect coverage bought.

Prevention in `pre-commit-checks.sh` — REJECTED on the intake's own AC-003. A
pre-commit predicate is a HARD GATE by construction; it would block a commit on
a machine whose generators are absent. Also a `protected_paths_l3` surface, so
it buys the same ceremony bill for a worse property.

Prevention in `allocate-doc-number.mjs` — CHOSEN. The rename is the event that
invalidates the projections; regenerating there closes the window to zero, and
every commit downstream of allocation is born fresh. It is not new machinery:
the function `regenerateIndex(root)` (line 790) already does exactly this for
`docs/INDEX.md` with an `fs.existsSync` guard and a swallowed failure, and it is
already called from exactly one place (line 1111) that `--dry-run` returns
before reaching (line 1072) and that `--guard`, `--backfill` and `--reserve`
never enter.

The cost, stated plainly: `.aai/scripts/allocate-doc-number.mjs` is on
`protected_paths_l3` in docs/ai/docs-audit.yaml, so per .aai/workflow/WORKFLOW.md
this spec MUST declare `ceremony_level: 3` — Planning RAISES the intake's
declared level 1. That means the full pipeline and a FULL_RUN CI selection
(`protected_paths_l3` is a `full_run_triggers` class in
tests/skills/suite-map.yaml). That is a ceremony bill, not a risk bill: the code
delta is one new best-effort function plus one call, at an existing call site,
in a code path that already performs the identical operation. Paying level 3
once is the honest price for putting the control where it actually works,
against a defect that recurred within six hours of being written down.

Detection is added because prevention is a single call site and the pages have
other writers (a hand-run generator, a future generator, a merge). Detection
carries no gate: it is a test in an existing suite.

If a generator is missing or slow on some machine: the allocator prints one
named line and exits with exactly the code it would have exited with before
(D2). The detection test is the only thing that can go red, and it goes red on
the artifact's CONTENT, not on the generator's availability — a repo whose pages
were never generated has nothing to flag.

### D2 — WHICH generators, in what order, and how failure degrades

The survey was run, not assumed. Every candidate was measured on this tree for
(a) whether its output embeds a spec PATH, (b) tracked-vs-ignored, (c) cost.

| generator | output | tracked | embeds a spec PATH | cost |
|---|---|---|---|---|
| generate-docs-index.mjs | docs/INDEX.md | tracked | YES (261 SPEC refs) | 9.13 s |
| generate-userguide-rollup.mjs | docs/USER_GUIDE.md | tracked | YES (41 SPEC refs, `[Spec](specs/SPEC-....md)`) | 0.04 s |
| generate-overview.mjs | docs/ai/overview.html + overview-data.json | tracked | YES (115 + 229 SPEC refs, `<a href="../../docs/specs/SPEC-....md">`) | 0.08 s |
| generate-factory-report.mjs | docs/ai/factory-report.html + -data.json | tracked | NO — bare ids only (`refs[]`, `lead_time.per_item[].ref`); zero `specs/` strings in the generator | 0.06 s |
| generate-dashboard.mjs | docs/ai/dashboard.html + -data.json | tracked | NO — zero `SPEC-` occurrences of any form in either artifact | 0.04 s |
| generate-docs-hub.mjs | docs/ai/docs-hub.html | present and tracked; its OUTPUT is neither on disk nor tracked (corrected post-freeze, validation F3) | NO — 0 `docs/specs` and 0 `SPEC-` strings, re-measured | n/a |

Chosen set: `generate-overview.mjs`, then `generate-userguide-rollup.mjs`,
appended after the existing `regenerateIndex(root)` at line 1111. The INDEX regen
keeps its current position and its current silent-degrade body — this scope does
not change it.

Order rationale: neither new generator reads the other's output (overview reads
`docs/{issues,rfc,specs,...}`, EVENTS, METRICS, STATE; the rollup reads
`docs/product/*.md`), so the order is a stability convention, not a dependency.
It is therefore taken from the one place the repo already orders these two —
`close-work-item.mjs` lines 1200-1201, overview before rollup — so no second
convention is invented.

Excluded on evidence: factory-report and dashboard. Running them would add
timestamp-only churn to every allocation commit and buy zero coverage of this
defect class; close-work-item already regenerates the factory report at close.
docs-hub is neither present nor tracked here, and a guard over an untracked file
is theatre.

Failure degradation mirrors `regenerateFactoryReportBestEffort()`
(close-work-item.mjs line 584) exactly, not approximately:

```
function regenerateSpecPagesBestEffort(root) {
  for (const gen of ['.aai/scripts/generate-overview.mjs',
                     '.aai/scripts/generate-userguide-rollup.mjs']) {
    try {
      const abs = path.join(root, gen);
      if (!fs.existsSync(abs)) continue;          // absent -> silent skip
      execFileSync('node', [abs], { cwd: root, stdio: 'ignore' });
    } catch (err) {
      process.stderr.write(`allocate-doc-number: INFO ${path.basename(gen)} `
        + `regen skipped (best-effort, non-fatal): ${err.message}\n`);
    }
  }
}
```

Same three properties: `fs.existsSync` guard so a core-only sync silently skips;
every throw swallowed into ONE named INFO stderr line; the exit code never
changes and no rollback path is reachable. Total added cost on this tree:
0.12 s on top of an allocation that already spends 9.13 s regenerating the INDEX.

Accepted cost, written down: `generate-overview.mjs` stamps a `Generated
<ISO timestamp>` into both its artifacts, so every allocation commit will now
carry a two-file timestamp diff even when no spec path moved.
`generate-userguide-rollup.mjs` is byte-idempotent (verified: a no-op re-run
leaves `docs/USER_GUIDE.md` unchanged), so it adds churn only when content
actually changed.

### D3 — the detection test's precision

The predicate, stated as the test will implement it:

For each path in the CLOSED list below that EXISTS and is git-TRACKED, extract
every `<TYPE>-DRAFT-<slug>` token. Report a violation for a token only when a
numbered counterpart `docs/<dir>/<TYPE>-<digits>-<slug>.md` exists on disk. A
token whose `docs/<dir>/<TYPE>-DRAFT-<slug>.md` still exists and has no numbered
counterpart is a legitimate in-flight draft and is NOT a violation.

The closed list is exactly the intake's AC-002 set:
`docs/USER_GUIDE.md`, `docs/INDEX.md`, `docs/ai/overview.html`,
`docs/ai/overview-data.json`, `docs/ai/factory-report.html`,
`docs/ai/factory-report-data.json`, `docs/ai/dashboard.html`,
`docs/ai/dashboard-data.json`. An absent member is SKIPPED with a named INFO
line, never a failure — the check must be portable to a checkout that has never
generated a page.

Two precision boundaries, both of which have a live counterexample on this tree
and both of which get a test:

1. The corpus is never scanned. `SPEC-DRAFT-` is legitimate, permanent prose in
   `docs/specs/**`, `docs/issues/**`, `.aai/**`, `tests/**` (the template teaches
   the convention; six suites assert on DRAFT literals as fixture data). A
   repo-wide grep would fire on all of it. The check reads only the eight paths
   above.
2. Non-generated runtime state is never scanned. The specific counterexample
   this spec cited at freeze (a stale `SPEC-DRAFT-spec-followup-registry.md`
   pointer in `implementation_strategy.rationale`) has since been overwritten
   by later rides — but the rule is MORE justified than at freeze, not less:
   validation re-measured `docs/ai/STATE.yaml` and found **34** DRAFT tokens
   whose numbered counterpart exists today (corrected post-freeze, F3). Any one
   of them would be a true positive
   under a naive predicate and a false alarm in fact, because STATE is a
   point-in-time record, not a published page. It is not in the list.

The slug match is exact and anchored on the slug, not a prefix: `SPEC-DRAFT-foo`
must not be satisfied by `SPEC-0001-foobar.md`.

### D4 — where the ordering is documented

Three places, all machine-adjacent, none relying on anyone remembering:

1. `.aai/SKILL_PR.prompt.md` step 1b — the ceremony text an agent reads at the
   moment of allocation. Its current claim ("...rewrites references, and
   regenerates docs/INDEX.md") becomes incomplete the moment this lands, and its
   next bullet ("Update the in-scope list: DROP the `*-DRAFT-*` path, ADD the
   `<TYPE>-000N-<slug>.md` path (+ docs/INDEX.md companion)") is LOAD-BEARING:
   staging is scope-only, so if the newly regenerated pages are not added to the
   in-scope list they never reach the commit and the whole fix is inert. Both
   lines are updated and both are grep-pinned by a test.
2. The allocator's own completion line, which today reads
   `allocate complete: N draft(s) numbered; docs/INDEX.md regenerated.` It will
   name every page it actually regenerated, so the exact stage-me list is
   carried on stdout rather than remembered. This is the anti-discipline half of
   point 1.
3. The allocator's file header comment block, next to the rename it guards.

`docs/product/` gains nothing: the intake is `user_visible: false`, no product
doc describes the close ceremony's ordering today, and inventing one would be a
fourth place to drift. No `docs/knowledge/LEARNED.md` rule either — a learned
rule is precisely the "recorded lesson that nothing enforces" the owner
rejected.

### D5 — close-work-item.mjs is NOT touched, and that is the AC-004 guarantee

The intake's AC-001 offers "close-work-item regenerates OR warns". Both arms are
declined, deliberately, and the spec pins the file's diff as EMPTY.

Its transaction (D6, lines 1139-1191) snapshots every doc's bytes plus the
EVENTS.jsonl BYTE LENGTH and rolls back by `fs.ftruncateSync` to that length.
CHANGE-0142's own D5 refused to widen that arm for exactly this reason, and this
repo carries a learned rule about restoring EVENTS.jsonl wiping close telemetry.
A warn arm would additionally have to resolve the ref's spec slug and read four
generated artifacts inside a function whose failure mode is a truncate.

The measured facts make the trade one-sided: close already regenerates both
spec-path generators, and it ran in both incidents without helping, because it
runs after `gh pr create`. Adding a warning there would fire after the bots have
already commented — the exact failure this scope exists to remove. The intake's
"close path" is satisfied by fixing step 1b of the same ceremony.

Consequence pinned as a test, not a promise: `git diff <base-ref> --
.aai/scripts/close-work-item.mjs` must be empty, and
`tests/skills/test-aai-close-work-item.sh` must exit 0 unchanged.

### D6 — everything is locally provable

No arm of this spec needs a network, a PR, a bot or a merge. The two real
incidents are replayed from local git history (`git show 00bdd03:...`,
`git show ff8208e:...`) with a byte-exact static fixture as the hermetic
fallback when those objects are absent (shallow clone) — the fallback always
runs, the history arm runs when reachable and degrades with a named INFO line.
Allocation is exercised in the suite's existing isolated fixture repo with a
local bare origin (zero network). Generator cost and idempotence are measured by
running them. The full command list is in `## Verification`.
