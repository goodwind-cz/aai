## 2. N3 — the RUN_ID hex collision. Assessed and reproduced.

**How the probe decides.** `deliveryCitationToken` (docs-audit-core.mjs:440)
matches every boundary-delimited run of 7-40 lowercase-hex chars
(`HASH_TOKEN_RE`, :419) and probes each with
`git rev-parse --quiet --verify <tok>^{commit}` (via `git()` at :295, stderr
discarded, any failure -> null). A token counts only if git resolves it to a
unique object that peels to a commit. An ambiguous prefix makes git error, so
that case fails safe. A prefix that uniquely names a blob or tree also fails
safe (`^{commit}` cannot peel it).

**Collision surface.** This repo's canonical RUN_ID is
`test-$(date -u +%Y%m%d-%H%M%S)` (tests/skills/test-framework.sh:661), so the
8-digit date is ALWAYS a boundary-delimited all-hex candidate; the 6-digit
time is not (below the 7-char floor). Measured here: 1036 commits, 0 whose
SHA starts with `2026`, so the guard is clean on this repo today. The
per-token probability is N/16^8 (~2.4e-7 at N=1036, ~2.3e-4 at N=1e6). Over a
project's lifetime of distinct RUN_ID dates it stays sub-1% for realistically
sized repos. Note the pre-existing timestamp convention `20260826T222200Z` is
immune (the trailing `T` breaks the lookahead), which is presumably why this
was never hit — the RUN_ID shape the amended prose newly invites is not.

**Reproduced.** In a local clone (commit `22503573...` exists), a cell reading
`RUN_ID test-22503573-120527 — docs/ai/tdd/green-20260101T000000Z-a.log`
produces:

```
AC-FLIP FAIL — docs/specs/SPEC-7777-n3.md is still open (status: implementing) but its AC Status table already reads as DELIVERED:
- Spec-AC-01: Evidence cites the delivery-grade token "22503573" — RUN_ID test-22503573-120527 — docs/ai/tdd/green-20260101T000000Z-a.log
Remediation: at hand-off, cite the PROOF artifact instead — the Evidence cell must carry a docs/ai/tdd/*.log path; a RUN_ID or suite output path may accompany it, never replace it.
```

**Diagnosable, or does it look like the defect?** Half-diagnosable. The output
NAMES the token, which is the single thing that makes it recoverable — an
agent can see `22503573` is its own RUN_ID's date. But the Remediation line is
a no-op for this cell: the cell already carries a `docs/ai/tdd/*.log` path and
already has the RUN_ID merely accompanying, which is precisely what the line
prescribes. Nothing in either prose surface says "and nothing in the cell may
resolve to a commit". So the agent is handed a guard that refuses a cell its
own instruction certifies — the Art. 4 / no-fixed-point failure this ride
exists to remove, recurring on a rarer trigger.

**Disposition recommended: promote to a follow-up ref, P3**
(`fu-acflip-runid-hex-false-positive`). NOT remediate-in-tree: the candidate
selection lives in `deliveryCitationToken`, which `falseOpenEvidence` shares,
so narrowing it would move the audit's own verdicts — a change that needs its
own scope and its own corpus proof. NOT an accepted residual either: it bites
(blocks a hand-off) rather than merely weakening assurance, and H6(d) is for
findings with no bite. The cheap, zero-risk mitigation for whoever takes the
follow-up is message-only — add one clause to the two prose surfaces and the
printed Remediation naming the escape ("if the named token is part of a RUN_ID
or a filename and not a commit you cited, remove or reshape it"), which
resolves the fixed point without touching predicate semantics.
