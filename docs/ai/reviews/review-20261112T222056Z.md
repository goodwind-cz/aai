## Findings

### B1 (BLOCKING) — the digest can never be clean at the point it runs, which makes the promotion score meaningless

- Where: `.aai/scripts/evidence-digest.mjs:103` (`if (status !== 'done') notDone += 1`), `:123` (the docs-audit `--gate` counted red), `:138` (sweep_owed), `:167-189` (`scoreEvents`: eligibility = pairs ≥ 20, rides ≥ 5, clean_fail = 0).
- Mechanism: VALIDATION's AC-FLIP DEFERRAL keeps every opted-in spec's AC rows `planned` until the close flip, which happens after validation. So at every validation digest, `acs_not_done = acs` and `docs-audit --gate` exits 1 (Rule-1 rows only). That makes `clean=false` structurally. With no clean digests, `clean_fail` is always 0, and the only promotion guard that carries information can never trip. After 20 pairs over 5 rides the score prints `PROMOTION eligible reason=ok`, but nothing has been measured.
- Evidence: this ride's own digest at its validated head is `acs_not_done=14 … gates_red=1 … clean=false`. The cause is only the planned rows: evidence_missing, tests_unlocated and the other gates are all 0. The r2 validator recorded the same line.
- backed-by: repro `/private/tmp/claude-501/-Users-ales-Projects-aai/2071b3a2-d378-409f-946d-cd8edb99948a/scratchpad/repro/repro-digest-vacuous-promotion.sh` exits 1. Part 1 reproduces the live clean=false; part 2 gives `clean_pass=0 clean_fail=0 pairs=20 rides=5 reason=ok`. The orchestrator should copy it under docs/ai/reviews/ so the backing stays durable.
- Why BLOCKING and not a follow-up: the shadow period exists to gather the false-pass signal, and it starts recording the moment this merges. Every shadow line recorded under the current clean rule is unusable once the rule is fixed, so a follow-up fixed later throws away the whole measurement window. The CHANGELOG also tells consumers that promotion needs "20 clean paired verdicts", which the code does not enforce. That is a false record.
- Fix direction (needs a spec amendment of D-DIGEST/D-SCORE; additive-with-disclosure, owner sign-off owed):
  1. Mirror the AC-FLIP DEFERRAL carve. While the spec frontmatter status is `draft` or `implementing`, a `planned`/`implementing` row does not count toward `acs_not_done`. A docs-audit `--gate` exit whose every reason is a Rule-1 non-terminal row does not count as red. `evidence_missing`, `tests_unlocated`, spec-lint and mutation-gate keep their full weight.
  2. Count eligibility on clean digests only, i.e. `clean_pass + clean_fail >= PROMOTION_MIN_PAIRS` (and rides counted over clean pairs). Only a clean digest tests the false-pass hypothesis.
  3. VALIDATION shadow wording: "run it after the round's sweep step, before the verdict". This removes the structural sweep_owed flag (see NB3).
  4. Add a TEST-3644/3646 fixture: an implementing spec with planned rows and complete evidence → clean=true; 20 flagged-only pairs → `min-pairs`.
- If the orchestrator/owner instead demotes it: follow-up `fu-digest-clean-unreachable-mid-ride`, P1. Also correct the CHANGELOG sentence now so it does not claim a gate the code lacks.

### NB1 — CHANGELOG states three false things (text-only; fix-now)

`CHANGELOG.md:35-38`:
- (a) "The value `default`, or any value outside low, medium and high, resolves null with one stderr NOTE". In fact `default` resolves null silently, and only out-of-vocab values print a NOTE (orchestration-dispatch.mjs, the effort-row branch).
- (b) "`state.mjs append-run` and `log-tick` accept `--requested-effort`, `--effort-applied`, `--cache-read` and `--cache-creation`". log-tick gains only `--cache-creation`. `--cache-read` already existed and now rejects negatives. requested-effort and effort-applied are append-run only, and log-tick would exit 2 on them.
- (c) "Promotion to `on` needs 20 clean paired verdicts". See B1. Either fix the code (B1) or say "20 paired verdicts".
- Disposition: remediate in tree (text-only).

### NB2 — a null harness_effort is never recorded as not_supported

`SKILL_LOOP.prompt.md:362`: the record clause sits inside "Dispatch carries `harness_effort`?". D-RECORD defines `not_supported` as including "harness_effort was null". As written, a Cursor or unknown-harness dispatch, or a consumer file without `effort_params`, records nothing. Its runs then land in `unset` beside the pre-change history, and the remeasure cannot separate "no knob" from "orchestrator ignored canon" (R1).

- Disposition: follow-up `fu-effort-null-harness-unrecorded` (P3), or fold it into the B1 remediation round.
