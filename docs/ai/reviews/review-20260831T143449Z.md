### NB-1 — non-ASCII em dash in a BOM-less PowerShell script
`.aai/scripts/aai-sync.ps1:633`

The new comment block contains `— the root cause of the reported drift`. Measured:
`aai-sync.ps1` had **0** non-ASCII lines at a8457c3 and has **1** at head, so this
diff newly enrolls the file in PSScriptAnalyzer's
`PSUseBOMForUnicodeEncodedFile` warning (visible in the ps1-quality run output
alongside the four .ps1 files that already trip it).

Failure scenario: Windows PowerShell 5.1 decodes a BOM-less `.ps1` with the system
ANSI codepage, so the three UTF-8 bytes become mojibake in the copy vendored into
every downstream Windows project — the same file the `windows-5_1` CI job
parse-checks. It is comment-only, so nothing parses or executes differently, and
the spec's 5.1 mandate is about *constructs*. But every other comment this diff
adds (in `gitignore-block.sh`, `aai-bootstrap.sh`, `aai-sync.sh`, and even the
adjacent `aai-sync.ps1:668` comment) already uses `--`, so this is a one-character
slip against the diff's own convention.

**Recommended disposition: (a) remediate-in-tree** — replace `—` with `--`.

### NB-2 — bash reconcile does not tolerate a CRLF `.gitignore` (pre-existing)
`.aai/scripts/lib/gitignore-block.sh:63`

`grep -qxF "$line" "$gitignore_path"` matches without stripping CR. The sibling
blocks in the very same sync script use `tr -d '\r' < "$DST_ROOT/.gitignore" | grep -qxF`
(`aai-sync.sh:588`, `:609`) and the new PowerShell block uses the `\r?$` anchor
(`aai-sync.ps1:656`) — this one path does neither.

Measured failure scenario: a target `.gitignore` with CRLF endings containing
`docs/ai/briefs/**`, synced three times with `bash .aai/scripts/aai-sync.sh <target>`,
ends with **4** occurrences of that pattern. The mechanism is a loop: the reconcile
appends LF lines, then the script's own self-heal at `aai-sync.sh:623+` detects
`gi_crlf=1` and rewrites the whole file back to CRLF, making the lines it just
wrote invisible to the next run. Every list pattern outside the self-heal's
`$aaiManaged` set (roughly 24 of 29) grows by one line per `/aai-update`,
unbounded.

**This is pre-existing, not a regression.** The identical fixture on the base tree
(`a8457c3`) produces the same `docs/ai/briefs/** = 4` — and 3 marker lines where
the head tree produces 1. The frozen spec mandates CRLF tolerance only for the
PowerShell block ("Target `.gitignore` uses CRLF. The PowerShell block must match
with the `\r?$` anchor"), and explicitly puts "any refactor of `aai-sync.sh` …
beyond the gitignore section" out of scope. I am recording it because the defect
now physically lives in a file this diff created, and because the diff's own
PowerShell half proves the correct treatment two files over.

**Recommended disposition: (b) promote to a typed `docs/ai/decisions.jsonl`
follow_up, severity P2** (real, measured, unbounded growth on a live platform;
but out of this scope's frozen boundary, so not remediate-in-tree here).

`.aai/scripts/aai-sync.sh:545`

Spec-AC-07's "or the shared library is absent" half is proven for bootstrap

### NB-4 — TEST-011's own guard can die without naming what it caught
`tests/skills/test-aai-sync-seed.sh:458,460`

```
referencers="$(find "$PROJECT_ROOT/.aai/scripts" -name '*.sh' -print0 \
  | xargs -0 grep -lF 'RUNTIME_IGNORE' 2>/dev/null | sort)"

```

Neither carries `|| true` under the suite's `set -euo pipefail`.

Failure scenario: if a refactor removes the last `RUNTIME_IGNORE` reference from

`grep -l` exits 1, `pipefail` propagates through the command substitution, and the

the operator gets an unexplained abort instead of the guard's own diagnosis. Note
the neighbouring TEST-016 already guards the same shape with `|| true`
(line 619-620), so this is an internal inconsistency rather than an unknown pattern.

**Recommended disposition: (a) remediate-in-tree** — append `|| true` to the
`xargs … grep -lF` pipeline and to the `grep -c .` substitution, matching
TEST-016.
