## `parseIssueUrl` read as code (`:295-324`)

Certification order is userinfo (raw + percent-decoded) → exact host pin → digit cap →
case-insensitive destination match. Findings from reading it as code, not as an argument:

- **First-line rule is correct**: leading blank lines are skipped, then the first non-empty
  line either matches or returns `unparseable`; no `continue` past a non-match (TEST-055).
- **Malformed/empty `destination`**: `!destination` refuses. Unreachable in practice — the
  publish path cannot reach `issue create` with an empty destination (`dedupSearch` at `:346`
  refuses first) — so it is a belt-and-braces guard, correctly fail-closed. A destination with
  a third path segment, or stray whitespace, degrades to the NOTE rather than mis-certifying.
- **Ordering**: only the *reason text* depends on the order (validation W-05 confirms
  TEST-052 pins it). The digit cap sitting before the destination check means a foreign repo
  with a 60-digit number reports the number reason; cosmetic only.
- **The decode `catch` at `:307`** is where the comment and the code disagree — NB-2.
- **By construction**: I re-derived it independently. `\d` is ASCII-only without `/u`; JS `$`
  without `/m` admits no trailing newline; `[^\s/]+` *does* admit NUL/ESC/NEL, so the exact
  equality on host and owner/repo is the only thing holding the ANSI/control-character
  argument up — which is why Amendment 4's two exactness fixtures matter, and why they are
  the right call. The claim holds with exactly one measured exception (NB-3).
