## Verdict 2 — code_quality: PASS

### The hoist (the risky part) — verified, no regression

`metrics-flush.mjs:971-991`. The DEFAULT-gate block now sits above
`if (inLedger.has(ref)) { toResume.push(entry); continue; }`. Purity audit:

- Inputs are all loop-invariant reads taken before the loop (`vStatus`, `vRef`, `rRequired`,
  `rStatus`) plus two per-entry reads (`ref`, `entry.runs`).
- `refMatches` (metrics-flush.mjs:282-285) is total and pure — it null-guards both arguments
  and cannot throw.
- `entry.runs` is initialised to `[]` for every entry by `parseMetricsEntries`
  (metrics-flush.mjs:223), so `.length` on a resumed entry cannot throw. This matters: the
  hoist made that read reachable for refs it previously never touched.
- `defaultReason` is `let`-scoped inside the loop body, so nothing leaks across iterations.
- The only write the hoisted block performs is `defaultOkRefs.add(ref)`. No `skipped[ref]`
  write, no push, no `continue`.

Combined with the six-lane differential above, the "pure read of loop-invariants" claim is
sound. This was the finding class most worth checking and it is clean.

### Is the allowlist closed under new lanes? — yes, and fail-closed in the right direction

`defaultOkRefs` is written at exactly ONE site (`metrics-flush.mjs:991`) under exactly one
condition (`defaultReason === null`). Every entry that can reach `toFlush` or `toResume`
passes through that site first — the sweep branch is downstream of it, and the only earlier
`continue` (`--ref` restriction) removes the entry from both sets entirely. Therefore:

- A lane added BELOW the add-point can only push refs whose default-gate answer is already
  recorded. If the ref did not satisfy it, no record. Fail-closed.
- A lane added ABOVE the add-point that short-circuits into `toFlush`/`toResume` bypasses the
  add entirely, so the ref is absent from `defaultOkRefs`. Also fail-closed.
- The only way to break the invariant is to write `defaultOkRefs.add(...)` from somewhere
  else, which is a visible edit to a single-purpose set.

The framing ("a subtraction must enumerate every lane that must not archive; an allowlist
enumerates the one that earns it") is not just rhetoric here — it is a property of where the
write sits, and it holds against the code. M1 in the mutation matrix is the empirical proof
that the subtraction did not have it.

### The hardcoded `verdict: 'PASS'` — I concur with keeping it, on two of the three grounds

A durable ledger asserting `verdict: PASS` for rides that never validated IS uncomfortable,
and this ride makes that field gate-bearing (binding 3). Judging it independently:

- **Round 2's recommendation would not have closed B2.** Correct, and the spec's argument is
  the right one: reproduction (d)'s corroborating line is a *genuine* default-flush PASS, so
  re-typing sweep lines leaves it untouched. A fix that must be paired with the allowlist
  cannot be the reason to drop the allowlist. Upheld.
- **It is SPEC-0068's field and the factory report's input.** Re-typing it from inside a
  frozen spec about a different lane is a second unsigned product-intent change. This is the
  strongest of the three reasons and on its own would justify the restraint.
- **"With the allowlist it adds no protection to this gate."** Nearly true, and the caveat is
  exactly finding N1 above: because binding 3 matches the ledger against `scopeRef` rather
  than `rec.ref`, a swept line CAN still be the corroborating hit in the `/`-joined-scope
  shape. That path needs a hand-edited STATE, so it lives inside R5, but the sentence is one
  notch more absolute than the code supports.

Net: keeping it is right, and `fu-sweep-ledger-verdict-typed-pass` is the right place for it.
My one reservation, recorded and not raised as a finding: P3 reads a notch low for a field
that is now gate-bearing; P2 would be defensible. It does not affect merge readiness.
