## The four items handed over, judged independently

**1 — The never-gate constraint.** The mechanism is right and the arm is real: it bites on both a `.mjs` and a `.ps1` gate, and its failure message names the incident it guards. The SET is wrong. Eight further gate-shaped scripts sit unnamed in the same `core:` profile list, two of them self-describing as gates in their own first line, and a heartbeat reference planted in `lane-gate.mjs` leaves the suite green. The fix is to INVERT the list: sweep `.aai/scripts/**` deny-by-default with an explicit allowlist of `heartbeat.mjs` plus the sanctioned `generate-live-status.mjs` seam. That is strictly stronger, covers a gate added tomorrow automatically, and — verified above by corpus grep — passes as-is today. The spec's D6 prose ("Spec-AC-08 makes 'no gate reads this' a MECHANICAL, failable check") and the function name `test_012_no_gate_reads_the_heartbeat` both read as the universal negative; only the `log_pass` string is scoped honestly to "named gate scripts". I did NOT rank this BLOCKING under the review prompt's universal-negative rule, because the spec's Test Plan row and Spec-AC-08 both enumerate the file list explicitly, so the registered claim is scoped — but the name and the D6 sentence should follow whichever way the set goes.

**2 — Deliberate absences.** Right call, and I found no creep. `read` prints `age_seconds` as a fact and defines no threshold anywhere; `GC_WINDOW_MS` is a GC window that never reaches the output; there is no `clear`, no lease, no `--exit-nonzero-if`. The one thing worth naming is not creep but the mirror of it: the 24 h GC means a slot silently VANISHES after a day, so a `read` on a long-idle ride prints "none recorded" — indistinguishable from never-written. Harmless at ride timescales; INFO only.

**3 — The dropped `isMain` guard.** "Drop it" is the better call here, and I would not have added the house pattern. `runMain` is a pipe-safe main runner, not a main-guard; the file exports nothing, so an import buys a caller only side effects and no value; and `git grep` confirms no importer. The theoretical bite — a future `generate-live-status.mjs` heartbeat panel taking the seam by IMPORT rather than by exec, and thereby running `main(process.argv.slice(2))` in the generator's process — is not reachable through a zero-export module. Not a finding.

**4 — Sanitization.** The character class is right for the job (`[A-Za-z0-9._-]`, everything else to `-`): path traversal is neutralized (`../` becomes `..-`, verified), and the slot name is shell- and filesystem-safe. `read --ref` cannot under-match, because both sides apply the identical sanitize+slice — Validation's check holds. Storing the SANITIZED `ref_id`/`role` rather than the raw values is correct and the reason given (a bidi override in a ref would defeat the message sanitization printed beside it) is sound; TEST-005 makes that non-vacuous by dirtying the ref and role too, and by asserting the surviving text as well as the stripped bytes. What the sanitizer does NOT have is injectivity, and nothing records that: see N3. Two refs differing only in punctuation, or only past character 64, collide into one slot and the second write silently wins, with no trace in the payload or the reader. The 64-char slice is not a live truncation hazard for this repo's actual ref_ids (longest in play is well under 64) but it is a second collision route.

**5 — The reaper epoch export.** The reasoning is mechanically sound and I confirm it from the code. `test-aai-run-tests.sh` TEST-005 (line 230) invokes the reaper with `AAI_REAP_WORKSPACE` and `AAI_REAP_MIN_AGE_SECS=0` and deliberately does NOT set `AAI_REAP_STEP_START_EPOCH` — it is testing the legacy path. An EXPORTED variable is inherited by that invocation, and `aai-reap-tests.sh:225-231` switches to EPOCH MODE on any valid value, which reaps only `start_epoch < STEP_START - GRACE`. TEST-005's `match_pid` is spawned MINUTES AFTER a step-start captured at the top of the validation step, so it is spared, and the arm fails at exactly "reaper failed to kill the in-workspace vitest proc". Deterministic, not load-dependent — which matches the reported 5/5-with, 0/2-without. The same inheritance also makes TEST-018's `UNSET` case a lie. Corroborating datum from this review: my own sweep did NOT export the variable and TEST-005 passed. What is NOT established is the CI attribution — this repo's workflow runs `test-framework.sh` directly and would not carry the export, so the mechanism explains validator-run failures cleanly and the "CI-load flake" only by conjecture. P2 and out of scope is the right disposition; I would narrow the follow-up's claim to the validator-run case and keep the CI question open inside it.
